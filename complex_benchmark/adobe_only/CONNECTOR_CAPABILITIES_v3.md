## HTML → Adobe Express AUTHORING (Group 2: create_visual_design_express_skill → html_export_readiness_skill → export_html_to_express / import-claude-design-from-url)
**Headless:** FULLY HEADLESS [C]. Verified end-to-end with zero user interaction: get_account_type → "auth"; export_html_to_express accepts the document inline via the `html` string param and returns `express_url` + `doc_url` (URN) + `slide_count` + per-slide normalized HzHTML synchronously (no polling, no widget, no picker, no async job). The verification loop is ALSO headless: asset_search(entityScope:"CCAsset") finds the produced doc, asset_get_presigned_urls resolves its rendition, asset_inline_preview returns the rendered pixels back to the model — so an agent can SEE its own layout and self-correct without a human. Five live exports run in this audit, all synchronous, all successful. The only "ask the user" step is the skill's POLICY instruction to AskUserQuestion about delivery destination — that is a workflow convention, not a technical gate; the tool never blocks on it. Caveat: there is NO headless way to get a file out of the finished Express doc — download_design is not surfaced in this host, so the deliverable is an editable Express document + the source HTML, not a PPTX/PDF/PNG from Express.

**Call chain:** get_account_type (must return "auth"; "guest"/"noauth" hard-blocks export) → create_visual_design_express_skill (returns the authoring playbook; MANDATORY per routing doc) → find_fonts([family or PostScript names]) → get_fontkit_embed_url([{postscript_name}]) → author ONE self-contained HTML file → html_export_readiness_skill (MANDATORY immediately before EVERY export AND every retry) → export_html_to_express({docName, html}) → returns {express_url, doc_url, slide_count, slides[{index,title,html,width,height}]}. VERIFY LOOP (optional but cheap and fully headless): asset_search({entityScope:"CCAsset", query:docName}) → asset_get_presigned_urls([{id, sourceType:"acp", renditionUrl, mediaType}]) → asset_inline_preview({presignedUrl, size}) → model sees the rendered page 1. IMAGE SUB-CHAIN (required for any photo): local file → asset_initialize_file_upload → curl PUT each block href → asset_finalize_file_upload → presignedAssetUrl (at.adobe.com) → any image_* tool → outputUrl (photoshop-api.adobe.io) → curl -L the outputUrl locally → base64 → inline as a data: URI in the HTML. The URL must NOT be left as a URL in the HTML (see gotchas). Alternative entry: import-claude-design-from-url({url}) — same importer, url must be on *.claudeusercontent.com or *.adobe.com only.

**CANNOT:**
- PLACE A PHOTO BY URL — THE SINGLE BIGGEST TRAP. Every external image URL was replaced with a 1x1 transparent PNG placeholder and renders as an EMPTY GREY BOX in the finished Express document. Verified visually. This held for NON-allowlisted hosts (images.pexels.com, upload.wikimedia.org) AND for hosts the readiness skill explicitly allowlists: at.adobe.com (the connector's own asset_finalize_file_upload presignedAssetUrl) and photoshop-api.adobe.io (an image_crop_and_resize outputUrl). The documented image-fetch allowlist did NOT work in this environment. Only data: URIs actually render.
- CSS background-image WITH A data: URI IS DROPPED ENTIRELY — the element imports as an empty <div> with geometry and no image. (background-image with an http(s) URL does become an image shape, but with the placeholder — so both routes fail. Use an <img> tag with a data: URI.)
- text-decoration: underline — dropped silently.
- -webkit-text-stroke — dropped; combined with color:transparent the text becomes color="#00000000", i.e. completely invisible. Outlined/stroked display type is unachievable.
- outline (any style) — dropped entirely.
- filter: blur() — dropped (the element renders as a hard-edged solid).
- backdrop-filter (incl. saturate/hue-rotate) — dropped; only the underlying rgba background survives, as fill + opacity.
- mix-blend-mode — dropped; the element renders as a plain opaque shape.
- text-shadow — dropped.
- column-count / multi-column text — dropped; the text reflows as a single column (column-gap is retained but meaningless).
- MULTI-LAYER box-shadow — ONLY THE FIRST LAYER SURVIVES, verified at both 4 layers and 2 layers. Not 'partial support' — a hard truncation to layer 1.
- display:none and visibility:hidden elements are REMOVED from the document entirely (no hidden layer to toggle later).
- Any JavaScript, @keyframes animation, transition or inline event handler — not executed; the import is one static frame. onclick handlers are stripped; <script src> and inline <script> are ignored without error.
- Generic CSS font families are NOT honoured — font-family:serif;font-weight:700 resolved to SourceSans3-Bold (a SANS). cursive likewise fell to SourceSans3. An invented family name ('Grumbleflax Deluxe') silently became SourceSans3-Regular with no warning.
- true vertical typesetting — writing-mode:vertical-rl is approximated as transform:rotate(90deg) with a recomputed left, not real vertical text.
- Getting a FILE out of the Express document — download_design is NOT surfaced in this host (confirmed by name lookup), so no PDF/PNG/PPTX export of the finished Express doc through the connector. Neither is suggest_type_palettes nor get_type_palette. The deliverable is the editable Express doc + your own HTML.
- Responsive / adaptive layouts, dashboards, app UIs, wireframes — explicitly out of scope; the readiness skill routes these to a 'regeneration gate' that requires asking the user first.
- Feeding image_* tools an arbitrary public URL — they enforce their OWN separate domain whitelist and rejected both images.pexels.com and t3.ftcdn.net ('URL domain not whitelisted').

**GOTCHAS:**
- RIGHT/BOTTOM ANCHORING IS ONLY SAFE ON ELEMENTS WITH EXPLICIT WIDTH AND HEIGHT. Verified both directions in a dedicated probe: an <img width=200 height=200 style="right:120px;bottom:120px"> landed exactly right; a content-sized wrapper <div style="position:absolute;right:120px;top:160px"> around an inline SVG collapsed to zero width, kept right:120px, and its children ran clean off the canvas edge (clipped, half-visible). Auto-sized TEXT anchored with `right` also mis-resolved (importer wrote left:1776px on a 1920 canvas, pushing the string off the edge). RULE: anchor with left/top, or supply explicit width+height.
- INLINE SVG MUST SIT IN A WRAPPER WITH EXPLICIT left/top AND EXPLICIT width/height — or be a bare <svg> positioned directly with left/top. Verified: variants A (wrapper left/top + w/h), B (bare svg, no wrapper) and D (wrapper left/top + w/h) all rendered perfectly; variant C (wrapper right-anchored, content-sized) broke. In the first deck probe this same defect threw an SVG rect on top of the headline and pushed the circle off-canvas.
- get_fontkit_embed_url TAKES PostScript names BUT YOUR CSS MUST USE THE KEBAB css_stack IT RETURNS. Input {postscript_name:'PlayfairDisplay-Bold'} -> returns css_stack "playfair-display",serif. Writing font-family:'PlayfairDisplay-Bold' in the CSS would be treated as an invented name and silently fall back. The HzHTML then reports the resolved PostScript face, which is how you verify it took.
- FONT WEIGHT IS NOT INHERITED FROM HTML SEMANTICS. An <h2> with no explicit font-weight imported as SourceSans3-Regular, losing its browser-default bold. Always set font-weight explicitly on every text element. (font-FAMILY declared only on body DID propagate in this test, contradicting the readiness skill's warning — but weight did not, so declare both per element.)
- THE IMPORTER REORDERS position:sticky ELEMENTS. A sticky-positioned text node was hoisted to the FRONT of the slide's child list, ahead of the h1. position:fixed was kept verbatim with its fixed positioning. Never use either.
- SUCCESS IS NOT FIDELITY. Every one of these drops (images, blur, blend, stroke, underline, columns, shadow layers) returned HTTP success with no warning of any kind. You MUST parse slides[].html — and better, render-check via asset_search -> asset_get_presigned_urls -> asset_inline_preview.
- THE RENDITION PREVIEW SHOWS PAGE 1 ONLY. asset_inline_preview on the Express doc's rendition returns the first artboard; pages 2..N cannot be visually verified this way. Multi-page verification has to lean on the HzHTML.
- hz:slide-selector MUST NAME THE PER-ITEM CLASS, NEVER THE WRAPPER — content=".slide", not ".deck". Naming the wrapper collapses an N-slide deck into 1 slide.
- DO NOT PASS canvasWidth / canvasHeight / slideSelector AS TOOL PARAMS. They are GLOBAL overrides applied to every slide and they suppress the self-describing per-root data-canvas-* sizes — which is exactly what kills a mixed-size deck. Leave them unset and let the HTML declare.
- INLINE PAYLOAD SIZE: under 70 KB sends clean; at or over 70 KB the skill requires warning the user that the import may be slow or fail. Since every photo must be base64-inlined, a design with 2-3 real photographs blows past 70 KB immediately — plan for it (a 600x400 JPEG at q72 was already 51 KB of base64).
- ADOBE STOCK THUMBNAILS ARE ON t3.ftcdn.net, WHICH IS NOT THE ALLOWLISTED HOST. The readiness skill allowlists only the exact hosts as1.ftcdn.net / as2.ftcdn.net. Moot in practice, since no external URL resolved at all.
- image_* TOOLS HAVE A SEPARATE, STRICTER DOMAIN WHITELIST than the importer. Both images.pexels.com and t3.ftcdn.net were rejected outright ('URL domain not whitelisted'). An image must reach them via asset_add_file (picker), asset_initialize_file_upload (egress), or a LICENSED Stock URL.
- ONLY ONE <style> BLOCK, IN <head>. The only permitted external <link> is the Typekit stylesheet from get_fontkit_embed_url, embedded verbatim.
- html_export_readiness_skill IS MANDATORY BEFORE EVERY export AND EVERY RETRY — the routing doc calls a self-decided skip ('it isn't in my callable list, I'll proceed') a workflow violation, and both skills are deferred-loaded via ToolSearch, so absence from the visible list is never evidence of absence.
- THE REGENERATION GATE IS A HARD STOP FOR NON-FIXED-CANVAS INPUT. If the HTML is responsive/app/wireframe-shaped, the skill requires asking the user a verbatim question and WAITING before exporting. Any benchmark task whose HTML drifts responsive will stall on a user prompt.
- CSS custom properties DO resolve, contrary to the readiness skill's own table — var(--probe-accent) came through as #7FD1C1 and var(--probe-bg) as #14202B. The importer reads computed styles. Safe to use, but the doc says otherwise, so an agent following the doc may needlessly inline them.
- opacity:0 elements are KEPT but written as color="#00000000" — present in the document, invisible on the canvas. Not the same as display:none (which deletes the element).

## TYPOGRAPHY / Adobe Fonts (font_recommend, font_search, find_fonts, font_details, font_styles, font_preview, get_fontkit_embed_url)
**Headless:** FULLY HEADLESS — the cleanest [C] family in the whole connector. All 7 tools are synchronous request/response JSON. No file upload, no assetId, no presigned URL, no progress widget, no async poll, no user file-picker, no Express round-trip. Nothing in this family requires the user to touch anything. font_preview is the only tool that renders a card into chat, and that is cosmetic — every other tool returns data an agent consumes directly. get_fontkit_embed_url returns a real, publicly-fetchable, NON-domain-locked Typekit kit URL, so the resulting CSS is usable from any origin (verified from localhost with no Referer). NOTE: the session emitted a system-reminder claiming "plugin:adobe-for-creativity requires authentication / non-interactive". That is a FALSE ALARM — every tool call in this audit succeeded. Do not design around it.

**Call chain:** RELIABLE CHAIN (all verified live today):

1. get_account_type()  ->  {"account_type":"auth"}   [cheap, no auth needed, gates Express export later]

2. font_recommend({user_query, moods, text_hierarchy:"heading"|"body", per_page})
   -> 10 named buckets x 3 fonts = 30 candidates. Each candidate carries
      font_identifier{postscript_name, font_id}, family_name, style_name, full_name,
      designers, foundry, detail_url, preview_url.
   *** Call it ONCE PER TYPOGRAPHIC ROLE (heading, then body). Do not ask it to pair. ***

3. font_styles({font_identifier:[{postscript_name}, ...]})
   -> family{name,slug,foundry,designers,detail_url,language_support} + styles[] with the
      NUMERIC OpenType weight and library_availability{full,trial} per style.
   *** THIS STEP IS MANDATORY, NOT OPTIONAL. It is the only way to learn the numeric
       font-weight you must write in CSS. Skipping it silently ships the wrong weight. ***

4. find_fonts({font_names:[...max 20...]})
   -> per-name {available:true, postscript_name} | {available:false, unavailable_reason}
   *** Use this ONLY to launder names into canonical PostScript form. Its returned
       postscript_name is the ONLY string safe to hand to step 5. ***

5. get_fontkit_embed_url({fonts:[{postscript_name}, ...]})
   -> {kit_id, css_embed_code:"<link rel=\"stylesheet\" href=\"https://use.typekit.net/<kit>.css\">",
       families:[{web_id, name, css_names:["slug"], css_stack:"\"slug\",sans-serif"}]}
   *** ONE call for ALL fonts in the design. 25 families in a single kit verified OK. ***

6. Author HTML: paste css_embed_code VERBATIM into <head>; set font-family from
   families[].css_stack (the SLUG, never the PostScript name) and font-weight from the
   numeric weight learned in step 3, ON THE TEXT ELEMENTS THEMSELVES (not just body).

7. html_export_readiness_skill()  ->  8-section checklist. Its section 3 explicitly
   whitelists `<link rel=stylesheet href=https://use.typekit.net/...>` as the ONLY
   permitted external stylesheet, so the kit survives into Express intact.

8. export_html_to_express({html|url, docName})  -> native editable Express document.

MINIMUM VIABLE CHAIN: font_recommend -> font_styles -> get_fontkit_embed_url. find_fonts is
skippable when you already hold a postscript_name from font_recommend's font_identifier
(those are already canonical); it is REQUIRED whenever a name came from a human, a brief,
or your own memory.

- FRAME GRANULARITY FROM A PDF IS NOT UNDER YOUR CONTROL AND CAN COLLAPSE TO ONE FRAME. A continuous text flow (Chrome-printed HTML, no images) converted to exactly ONE TextFrame holding all six lines and ZERO graphic frames — so there was no way to map fields to distinct frames. Inserting images into the source PDF split the text into TWO frames plus TWO graphic frames. You cannot spec 'map the name frame and the title frame separately' unless the source PDF's visual blocks are actually separated. Always export IDML and look before promising a frame layout.
- convert_pdf_to_indd RETURNS A RAW .indd, NOT A ZIP, when embedLinks is left at its default false — despite the description saying 'Returns a ZIP containing the converted document and linked assets'. Verified: content_type application/x-adobe-indesign, `file` says 'Adobe InDesign Document'.
- PDF CONVERSION FAILS OPAQUELY ON THIN PDFs. 'Job failed' with no reason. Source PDFs must be real, well-formed, font-embedding PDFs. Budget a retry with a differently-generated PDF rather than debugging the error.
- document_render_layout PARAMETER INTERACTIONS ARE BRITTLE. pageRange:'1' works alone, but combining outputMediaType image/jpeg + quality:'maximum' + colorSpace:'CMYK' + pageRange:'1' produced '#/pageRange: expected type: String, found: Integer'. Dropping colorSpace and using pageRange:'1-1' succeeded. Prefer the 'N-N' range form and add optional params one at a time.
- THE MERGE IMAGE COLUMN NEEDS THE '@' PREFIX IN THE CSV HEADER ('@photo'), the cell holds a BARE FILENAME ('ava.png'), and additionalImageFiles keys must match that filename EXACTLY (the URL path need not contain it). Verified working with that exact shape.
- generate_indd_mapping_prompt RE-EMITS THE ENTIRE ~3,400-token instruction prompt ON EVERY CALL, including validation-only calls. Two calls cost ~7k tokens of pure boilerplate. Budget for it, and don't call it speculatively.
- document_merge_data_layout's description claims 'One output file per CSV row' — TRUE for image/png and image/jpeg, FALSE for application/pdf and application/x-indesign (both give one multi-page file). The summary text also mislabels a single multi-page PDF as 'Row 1 – PDF'.
- video_render's SCHEMA proves capabilities the connector's own Tool Limitations section denies. It accepted a two-clip timeline with sourceStart {n:20,d:1}/sourceDuration {n:3,d:1} then sourceStart {n:5,d:1} — i.e. trim-to-timestamp, out-of-order multi-clip assembly, per-clip audioTransform.gain (0..2), visualTransform scale fit/fill, rotate 0/90/180/270, arbitrary output width/height/framerate, 10-min max — while the routing doc still says 'Video trimming to timestamps — not available' and 'Video format conversion — not available'. The capability plainly exists server-side; it is simply UNRETRIEVABLE here. Do not design a task around it, and do not cite the old 'quick_cut is the only cutting tool' line as true either.

**COLLATERAL UNLOCKED:**
- A personalised print run from a client's existing PDF artwork with NO native InDesign file supplied — business cards, name badges, appointment cards, certificates, shelf labels, direct-mail pieces. This is the flagship unlock: the client hands over a flat PDF and a roster CSV, and the agent reverse-engineers it into a live merge template. Deliverable: one press PDF, N pages, page-count = row-count (grader-checkable exactly).
- The same run delivered as PER-RECORD FILES the agent names itself — one single-record PDF per person via createSeparateFiles, or a recordRange:'N' loop. Unlocks 'one print-ready file per staff member, named to the roster' as a real, gradeable deliverable.
- A VARIABLE-IMAGE collateral set: per-row headshots or per-branch logos bound through an @-prefixed CSV column + additionalImageFiles. Staff badge sheets, team card sets, product labels with per-SKU shots. Verified binding correctness — and the trap is that a naive agent will place one static image on every record.
- A DUAL-DELIVERABLE branding package from ONE merged .indd: the press PDF for the printer PLUS 300-DPI JPEG/PNG proofs per record for client sign-off — merge once to application/x-indesign, then render twice at different media types and resolutions.
- A TEMPLATE-ARCHAEOLOGY task built on export_idml: the agent must inspect a supplied .indd/.idml, report its real frame inventory (counts, bounds, applied fonts, object styles, existing links) and decide which frames can carry which fields. This is legitimate document-structure inspection through a supported channel — and it is the only honest way to justify a mapping.
- A CROSS-ASSET IMAGE-PREP + MERGE COMPOSITE: use the [C] image_* tools (straighten, tone, crop-to-bounds, remove_background) to normalise N raw headshots to one look, then bind those AGENT-PRODUCED outputs into the merge via a filename column the agent chose. Depth comes from the dependency — a badly prepped image is invisible until it lands in the layout at the wrong crop.
- A DELIBERATE OFFSET-INTEGRITY GATE (the strongest new benchmark idea here): give the agent a PDF whose converted template collapses several fields into ONE text frame containing a run that generate_indd_mapping_prompt drops. The naive agent trusts textContent, gets '✓ VALID' and 'completed successfully', and silently ships a template missing 2 of 6 fields. The correct agent round-trips the IDML, recomputes offsets from the true story text, and re-verifies placeholders after prepare. Failure is invisible in every tool response and only shows up on the merged output — exactly the wrong-DECISION, visible-downstream-breakage gate the hardness bar asks for.
- A FRAME-GRANULARITY TRIAGE: two superficially identical client PDFs, one whose text blocks are separated (yielding multiple mappable frames) and one whose text is a single flow (yielding one frame). They need different mapping strategies — per-frame replace_all-style mapping vs offset-based replace_text within one story. The agent cannot tell which is which without exporting IDML first.
